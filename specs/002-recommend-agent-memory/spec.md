## User Scenarios & Testing *(mandatory)*

### User Story 1 - 可纠正的结构化偏好记忆 (Priority: P1)

作为登录用户，我希望系统记住我的区域、品类、预算与忌口等偏好，并在后续提问中自动补全未说清的条件；当我说「忘掉预算」「我现在也吃辣」时，偏好必须被删除或纠正，而不是越积越错。本轮我明确说出的条件始终优先于历史偏好。

**Why this priority**: 没有可纠正记忆，多轮推荐无法证明「有记忆」的产品价值；错误偏好若不可撤销会直接伤害信任，也是面试高频追问点。

**Independent Test**: 在固定用户下写入初始偏好 → 用空缺条件提问验证补全 → 再发送纠正/清空话术 → 检查偏好终态与后续补全行为；可与推荐助手解耦，先在现有智能点评检索路径上验证「仅补空字段」。

**Acceptance Scenarios**:

1. **Given** 用户已有「海淀区 + 人均上限 100」偏好且本轮问题未提区域/预算，**When** 发起推荐或检索相关提问，**Then** 系统用偏好补齐空缺过滤条件，且不得覆盖本轮已明确给出的条件。
2. **Given** 用户说「忘掉预算」或等价清空表达，**When** 回合结束并完成偏好合并，**Then** 预算偏好被清空；后续提问不再自动套用旧预算。
3. **Given** 同一用户多个会话几乎同时更新偏好，**When** 各自合并完成，**Then** 最终偏好不因并发覆盖而丢失对方已成功合并的变更（允许重试后一致）；解析失败不得覆盖旧偏好。
4. **Given** 偏好加载失败，**When** 用户仍发起提问，**Then** 本轮仍可仅凭当轮条件继续，不得整单失败。

### User Story 2 - 有界多步店铺推荐助手 (Priority: P1)

作为登录用户，我希望通过专用推荐入口用自然语言提问，助手按需发现候选店、读取店铺详情或真实评价，在有限步数与调用次数内给出推荐；过程中只看到「正在检索 / 读取详情」等状态，看不到隐藏推理或原始工具吐出内容。

**Why this priority**: 这是第二阶段的核心产品面；相对单次 Hybrid 问答，多步工具选择才是 Agent 叙事主菜。

**Independent Test**: 登录后对同一会话发送需要「先搜再看详情/评价」的问题，确认在预算内完成、返回可读推荐，且未登录或空问题被拒绝。

**Acceptance Scenarios**:

1. **Given** 已登录用户与有效会话标识，**When** 提问需要对比候选并核对详情的问题，**Then** 助手可按需使用「搜店 / 读店铺详情 / 列店铺评价」三类只读能力，并在步数与工具次数上限内结束。
2. **Given** 助手已达到最大推理步数或最大工具调用数，**When** 仍未得到最终回答，**Then** 运行停止并返回可理解降级结果或错误，不得无限继续调用。
3. **Given** 未登录或问题/会话标识缺失，**When** 调用推荐入口，**Then** 请求被拒绝（未授权或参数无效），不消耗推荐推理。
4. **Given** 客户端中途断开，**When** 推荐运行尚未成功结束，**Then** 下游工作取消，且本回合不得写入长期偏好。

---

### User Story 3 - 推荐回答必须有据可查 (Priority: P1)

作为用户与维护者，我需要助手推荐的店铺引用全部来自本轮实际获得的候选/详情结果；不得编造未检索到的店，也不得在工具失败时假装成功。

**Why this priority**: 无 groundedness 约束的 Agent 无法对外宣称可信，也是相对单次 RAG 对照时必须守住的底线。

**Independent Test**: 构造「工具返回集合已知」的场景（含无结果、工具错误），检查最终回答引用集合是否为其子集，且无结果时明确说明而非硬凑。

**Acceptance Scenarios**:

1. **Given** 本轮工具结果中的店铺集合为 S，**When** 助手给出最终推荐，**Then** 回答中引用的每个店铺标识都属于 S。
2. **Given** 检索或详情读取失败，**When** 助手收尾，**Then** 不得编造店铺事实；应说明无法完成或给出不依赖虚假证据的降级说明。
3. **Given** 相同工具与相同参数已被调用过，**When** 模型再次请求，**Then** 系统拒绝重复执行该调用并计入轨迹约束，避免空转循环。

---

### User Story 4 - 可复现的 Agent 评测与对照基线 (Priority: P1)

作为维护者 / 面试演示者，我需要一份人工设计的多轮 Agent/记忆场景集，用确定性评分（任务结果、有据可查、轨迹预算、关键题多试次稳定性）跑出可复现报告，并与规格 `001` 的 Hybrid 生产口径检索/回答基线对照，用数字说明 Agent 相对单次 Hybrid RAG 的收益与代价（延迟、调用次数等）；不得用一次偶发跑分当结论。

**Why this priority**: 没有评测就无法兑现总计划的对外叙事；且须先有场景与评分定义，再实现助手，避免「做完再想怎么测」。

**Independent Test**: 在助手实现前后均可先跑评分器单测；助手接通后对正式场景集执行评测命令，得到含实验元数据与多 trial 汇总的报告。

**Acceptance Scenarios**:

1. **Given** 正式 Agent 场景集（约 10～15 条，覆盖记忆补全/覆盖/纠正、多步工具、无结果、工具失败、防循环），**When** 执行正式评测，**Then** 报告同时给出任务成功率（outcome）、有据可查率（groundedness）、轨迹合规（步数/工具数/重复调用）、基础设施失败率，以及成本侧延迟与调用量摘要。
2. **Given** 至少 5 条关键场景，**When** 各跑不少于 3 次 trial，**Then** 报告呈现跨 trial 成功率，不得只用单次结果代表稳定性。
3. **Given** 已冻结的 Hybrid 生产口径基线与本次 Agent 报告，**When** 撰写对照说明，**Then** 对照对象明确为 **Agent vs Hybrid RAG**（不是 dense vs hybrid），并固定题目集版本、模型与实验指纹等元数据。

---

### User Story 5 - 可演示的多轮记忆推荐与文档复现 (Priority: P2)

作为维护者，我希望用一条演示路径完成：登录 → 陈述偏好 → 同会话追问推荐 → 纠正偏好，并有文档说明如何复现评测与演示；可观测记录能支撑面试讲解一次成功与一次失败，且不泄露原始隐私正文。

**Why this priority**: 面试演示与知识落盘依赖完整闭环；可在 P1 故事可测之后交付。

**Independent Test**: 按文档步骤跑通三轮演示脚本，并核对脱敏后的偏好终态与可关联的追踪标识。

**Acceptance Scenarios**:

1. **Given** 文档中的演示步骤，**When** 在本地按步骤执行，**Then** 三轮分别体现偏好写入、记忆补全推荐、纠正/删除，且可打印脱敏偏好摘要。
2. **Given** 一次成功推荐与一次失败/降级，**When** 查看观测摘要，**Then** 能区分步骤数、工具名与状态、耗时与用量类指标，且不包含完整用户原文、完整偏好或评价正文。
3. **Given** 同一用户短时间频繁调用推荐入口，**When** 超过用户级频率限制，**Then** 请求被拒绝且不进入推荐推理。

---

### Edge Cases

- 偏好补丁中同一值同时出现「添加」与「删除」：删除胜出。
- 预算字段：未出现表示不变；显式清空表示删除上限；正数表示覆盖。
- 助手输出不得作为长期偏好的事实来源（只根据用户原话抽取补丁），避免把幻觉写回记忆。
- 场景题期望「无结果」：助手必须承认无合适结果，不得为凑答案放宽硬约束后假装命中。
- 工具超时或下游不可用：计入基础设施/工具失败路径，进入轨迹与可靠性统计，不把编造内容算成功。
- 最终回答生成后若未通过有据可查校验：不得把未校验内容当作成功推荐发出。
- 会话历史过长：必须按上下文预算裁剪，不能只按条数硬留导致关键约束丢失又超窗。
- 评测发现标注错误：不得为刷高分改期望标签；须记录原因并升级场景集版本。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 为登录用户持久化短期会话消息与长期结构化偏好（区域、品类、预算上限、忌口、摘要等），并具备可配置的过期策略（会话短、偏好长）。
- **FR-002**: 系统 MUST 支持偏好的添加、删除、清空与摘要更新；合并规则 MUST 明确「删除优先于添加」、预算的三态语义，以及「本轮显式条件 > 偏好补全 > 无条件」。
- **FR-003**: 偏好合并 MUST 在并发更新下保持安全（冲突可重试）；抽取/解析失败 MUST NOT 覆盖已有偏好。
- **FR-004**: 现有智能点评检索在用户已登录时 MUST 能用偏好仅补齐空缺过滤字段；偏好不可用时降级为仅本轮条件。
- **FR-005**: 系统 MUST 提供登录态推荐入口，接受问题与会话标识，并以流式状态/最终回答/完成或错误事件回传；MUST NOT 向客户端暴露隐藏思维链、原始工具结果或完整偏好原文。
- **FR-006**: 推荐助手 MUST 仅暴露三类只读领域能力：按条件搜索店铺、读取单店详情、列出单店评价；MUST NOT 把记忆读写做成模型可任意调用的工具。
- **FR-007**: 单次推荐运行 MUST 具备硬预算：最大推理步数、最大工具调用数、单工具超时、整次运行超时、工具结果长度上限；相同工具与相同参数 MUST 拒绝重复执行。
- **FR-008**: 最终推荐中引用的店铺标识 MUST 全部来自本轮工具观测集合；校验失败 MUST 视为失败/降级，不得当作成功回答发出。
- **FR-009**: 仅在推荐成功结束后 MUST 追加会话消息；长期偏好补丁在回合末由服务端抽取并合并，合并失败 MUST NOT 推翻已返回的主回答（记录告警即可）。客户端断连未完成的回合 MUST NOT 写偏好。
- **FR-010**: 系统 MUST 提供正式 Agent 场景集（约 10～15 条），覆盖记忆补全/覆盖/纠正、多步工具、无结果、工具失败、防循环等；每条含初始偏好、轮次、期望约束与标签。
- **FR-011**: 正式 Agent 评测 MUST 输出确定性评分：outcome（含终态偏好/硬约束）、groundedness、trajectory（步数/工具数/重复调用）、关键题多 trial 稳定性，以及延迟与用量类成本摘要；基础设施失败 MUST 单列且不进入质量分母。
- **FR-012**: 对外对照叙事 MUST 使用 **Agent vs Hybrid RAG（规格 001 生产口径基线）**；MUST NOT 将 dense vs hybrid 作为本规格验收或简历数字。
- **FR-013**: 每次正式 Agent 评测报告 MUST 含实验元数据：场景集版本与内容指纹、检索/模型相关标识、预算参数、样本量、trial 设置、基础设施失败数。
- **FR-014**: 推荐入口 MUST 做用户级频率限制；超限拒绝且不进入推荐推理。
- **FR-015**: 系统 MUST 提供可观测摘要（运行、模型轮次、工具执行、检索相关），属性限于状态与计量字段，MUST NOT 记录原始问题全文、完整偏好或评价正文。
- **FR-016**: 系统 MUST 提供可复现演示路径与说明文档，使维护者能一键/按步骤跑通多轮记忆推荐，并解释成功与失败样例。
- **FR-017**: 本规格范围 MUST NOT 包含：更换向量库、引入外部记忆/编排框架、用户事实向量记忆（Phase 2）、模型侧任意读写记忆工具、生成侧完整开放式质量 CI 强门禁、dense vs hybrid 对照交付。

### Key Entities

- **UserProfile（长期偏好）**: 某用户的结构化偏好与版本；支持补丁合并与纠正。
- **SessionTranscript（短期会话）**: 某用户某会话下的有序消息窗口，供多轮上下文。
- **ProfilePatch（偏好补丁）**: 由本轮用户原话导出的增删改意图，不是直接覆盖快照。
- **RecommendRun（推荐运行）**: 一次推荐请求的预算、工具轨迹、观测到的店铺集合、最终回答与用量。
- **DomainTool（领域工具）**: 搜店 / 详情 / 评价三类只读能力及其参数约束。
- **AgentCase（Agent 评测场景）**: 初始偏好、对话轮次、期望过滤/店铺/偏好终态与轨迹上限。
- **AgentReport（Agent 评测报告）**: 指标汇总、逐题/逐 trial 结果、实验元数据与失败摘要。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 维护者能在文档步骤下于一小时内跑完正式 Agent 场景集评测，得到含 outcome / groundedness / trajectory / 多 trial 稳定性 / 成本摘要与实验元数据的报告。
- **SC-002**: 在正式场景集上，引用店铺有据可查率达到 100% 的成功回答口径（凡标记为成功的推荐，引用集合均为本轮观测子集）；故意无结果/工具失败类题目不以编造计成功。
- **SC-003**: 至少 5 条关键场景各不少于 3 次 trial 的汇总成功率被写入报告；单次偶发成功不得作为对外稳定性结论。
- **SC-004**: 三轮演示（陈述偏好 → 同会话追问 → 纠正/清空）可重复执行，且第 2 轮体现补全、第 3 轮后偏好终态与纠正语义一致（抽检 3 次全过）。
- **SC-005**: 对同一批对照题，能给出 Agent 相对 Hybrid 生产口径基线的任务成功与代价对比（至少包含成功率与延迟或调用量之一），并标注固定实验条件；对照叙事中不出现 dense vs hybrid 数字。
- **SC-006**: 未登录调用推荐入口 100% 被拒绝；缺必填参数 100% 被拒绝；超用户频率限制时 100% 在进入推荐推理前被拒绝。
- **SC-007**: 达到步数或工具次数预算时，运行 100% 停止继续调用工具（抽样不少于 10 次强制触达预算的测试）。
- **SC-008**: 场景集规模在 10～15 条之间，关键类别（记忆、多步、无结果/失败、防循环）均至少 1 条；场景集内容指纹写入报告可核对。

## Assumptions

- 规格 `001` 的共享 Hybrid 检索入口与 `hybrid_prod` 基线可用；Agent 搜店能力复用该入口（含自动过滤抽取），本规格只追加「偏好补空」。
- 用户已通过现有登录态访问；推荐入口不另建账户体系。
- Phase 1 仅结构化偏好与会话，不做用户事实向量记忆；仅当真实失败案例证明结构化偏好不够时再另开规格。
- 默认预算采用源计划建议值（最多 3 步推理、5 次工具调用、单工具约 10s、整次约 45s、工具结果约 6000 字上限），实现期可配置但验收按默认值。
- 正式评测以本地开发机 + 既有编排环境为主；外部模型抖动存在，故 Agent 评测不作 PR 强门禁，以可重复本地/手工回归为主。
- 开放式措辞质量以人工抽检或可选评分辅助，不作为本规格硬门禁；硬门禁为 outcome / groundedness / trajectory。
- 源计划 `docs/plans/2026-07-11-recommend-agent-eval.md` Tasks 4–8 为实现细节参考，验收以本规格为准。

## Interview Value & Knowledge Capture *(mandatory for this project)*

### Interview talking points

- [ ] 为什么记忆不做成模型工具：服务端注入与合并，可校验、可限权、可纠正
- [ ] 有界 tool-loop：步数/次数/超时/去重，防止空转与成本爆炸
- [ ] Groundedness：先完整生成并校验引用，再作为成功推荐返回
- [ ] 评测组合：outcome + groundedness + trajectory + 多 trial；对照是 Agent vs Hybrid RAG
- [ ] 与后端主线的关系：登录、限流、分层、可观测，而不是「只会调模型」

- **blockers/**: 实现期按需（工具兼容性、并发偏好合并、断连与写偏好时序、评测抖动等）
